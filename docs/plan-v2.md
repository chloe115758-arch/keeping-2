## 1. 무엇이 바뀌었나

| | 이전 (v1) | 이제 (v2) |
|---|---|---|
| 서비스 | 등록한 약·영양제의 **겹침 확인** | 먹는 약·영양제로 **내 하루 복약 타임라인**을 만들고, 근거가 있는 만큼 **언제·어떻게 먹을지와 주의할 것**을 알려주는 복약 코치 |

## 2. 원칙 v2 (어기지 말 것)

### 2-1. 근거 등급

| 등급 | 근거 | 화면의 배지 | 말투 |
|---|---|---|---|
| **① 공식 지정** | DUR 병용금기, 임부금기 등 공식 지정 | "공식 지정" | 단정해서 말한다: "같이 복용하지 않도록 지정된 조합이에요" |
| **② 허가사항 근거** | 식약처 허가사항(설명서)에 적힌 복용 간격·식사 관계·상호작용 | "설명서 근거" | **구체적 행동을 제안한다** + 원문 한 줄: "칼슘 영양제는 12시 이후로 옮겨 보세요 (최소 4시간 간격)" |
| ②-참고 | 공식 기관의 복약 안내(허가사항 외) | "참고" | 제안하되 허가사항이 아니라는 것을 밝힌다 |
| **③ 근거 없음** | 위 어디에도 없음 | "확인 못 함" | **말하지 않는다.** "찾지 못했어요. 안전하다는 뜻은 아니에요" |

### 2-2. 지켜야 할 선

1. **모든 판단에는 등급 배지, 근거 원문 일부, 출처 링크, 확인일이 붙는다.**
2. **복용 중단, 용량 변경, 진단 같은 지시를 하지 않는다.** (설명서가 "용량을 늘려야 할 수 있다"고 적어도, 우리는 "복용량은 의사가 정해요"로 말한다.)
3. **"안전하다/괜찮다/문제없다/먹어도 된다"는 쓰지 않는다.** 근거가 없다는 것은 안전하다는 뜻이 아니다.
4. **판단은 규칙 코드가 하고, 문장은 사람이 원문을 대조해 만든 카드에서 가져온다.** 앱이 실행 중에 AI(LLM)를 호출해 문장을 만들지 않는다. AI는 카드를 만들 때 원문을 쉬운 말로 정리하는 데만 쓰고, 원문 대조는 사람이 한다.
5. 이상 증상이 있으면 약사·의사에게 가라는 안내를 항상 남긴다(타임라인 상세 맨 아래).
6. 임신·고령 같은 상태는 **더 보수적으로**: 근거 ①만 단정하고, 나머지는 "의사·약사에게 확인" 문구를 함께.
7. 확인하지 못한 것은 사실처럼 쓰지 않는다. 시연(미구현)은 화면에서 "시연"이라고 밝힌다.

### 2-3. 저작권·출처 (중요)

- 근거 원문은 **식약처 허가정보 API의 허가사항 본문**을 쓴다(공공데이터포털, 포털 표시 기준 이용허락범위 제한 없음, 개발계정 하루 10,000건). 약학정보원(health.kr) 같은 제3자가 편집한 화면은 저작권이 그쪽에 있으므로 **복제하지 않고** 필요하면 링크로만 참조한다.
- 병용금기 파일은 출처 표시 필수, 상업적 이용 금지 (기존 그대로).

## 3. 앱 흐름과 화면

### 3-1. 온보딩

| 단계 | 내용 | 비고 |
|---|---|---|
| O0 시작 | 시작하기 / **예시 사용자로 체험하기** | 시연 진입은 유지 |
| O1 저장 안내 | "이 기기에만 저장돼요" + 동의 | **기본정보(키·체중·나이) 수집 없음** |
| O2 약·영양제 등록 | ① **직접 검색**(기존 `dur.search`) ② **약봉투 촬영(시연)** | 4장 참고 |
| O3 복약 시간 | 약·영양제마다 시간 지정, 식사 시간(아침·점심·저녁) 설정 | 타임라인의 재료 |
| O4 상태(선택) | 임신 중 / 만 65세 이상 / 해당 없음(건너뛰기 가능) | 기본정보와 달리 **판단에 쓰인다**(임부·노인 주의). 건너뛰면 그 판단은 하지 않는다 |
| O5 루틴 생성 | "내 복약 루틴을 만들었어요": 아침·점심·저녁 약 개수, 주의 개수 요약 | 타임라인으로 |

### 3-2. 메인 = 타임라인 (깊이 3단계)

컨셉 저니(`ex.html`)의 타임라인 UI를 흡수한다. 시간이 세로로 흐르고 식사 위치가 함께 보인다.

| 깊이 | 보이는 것 | 열기 |
|---|---|---|
| **0. 행** | "아침약 · 08:00 · 약 3개 · 주의 2" + ⌄ | 기본 상태 |
| **1. 펼침** | 약별 한 줄: 이름, **식사 관계**(공복/식전/식후, 근거가 있을 때만), **핵심 주의 한 줄**(최대 1개 + "외 N건") | ⌄ 누르기 |
| **2. 근거 시트** | 근거 카드: 배지 · 헤드라인 · 상세 · 원문 일부 · 출처 링크 · 확인일. 맨 아래 "이상 증상이 있으면 약사·의사에게" | 주의 줄 누르기 |

- 타임라인 위에는 요약 한 줄만: "오늘 주의 N개". 행 위에 경고를 쌓지 않는다.
- 시간 간격 규칙이 어긋나면 **제안 시간**을 보여준다: "칼슘 영양제를 12:00 이후로 옮기면 간격이 4시간 이상이에요 (설명서 근거)". 사용자가 누르면 시간이 바뀐다(타임라인 슬라이더).
- 하단 탭: **홈(타임라인) · 내 약 · 마이** (3개).
- 타임라인에서 빼는 것: 운동 팁(공식 근거 데이터가 없다, 개선 방향), 혈당·혈압 등 건강 수치.

### 3-3. 새 처방 흐름

| 단계 | 내용 |
|---|---|
| N1 | **앱 알림(자동 연동)** — 시연: 잠금화면 알림 "새 처방약이 등록됐어요". 실제 연동은 구현하지 않고 "시연"이라고 밝힌다 |
| N2 | 알림이 없으면 앱에서: **약봉투로 추가(연습용 이미지 인식 시연)** 또는 **직접 검색** |
| N3 | 인식 결과 확인: 인식된 약 목록을 사용자가 확인·수정 |
| N4 | **타임라인에 반영**: 추가된 약이 하이라이트되고, 시간 배정 |
| N5 | **새로 생긴 주의** 요약: 조합 주의(① 병용금기, ② 설명서 간격)와 복용 시 주의사항. 깊이 2로 이동 가능 |

부차(최소 구현): 복약 체크, 질문 메모. 눈에 띄는 자리에 두지 않는다.

## 4. 약봉투 인식: 개선 방향이지만 **연습용 이미지는 인식되는 시연**을 넣는다 (결정)

- **실제 촬영·글자 인식(OCR)은 구현하지 않는다.** 이것은 개선 방향이다(시안의 처방전 인식 화면 `200:7004`, `305:5618`로 보여준다).
- 대신 **연습용 약봉투 이미지**(가상, `assets/ocr-demo/`, 3장)를 올리면 **인식한 것처럼 보여주고 → 약 검색으로 자동 이어지는 것**까지는 동작하게 한다.
  1. "약봉투로 추가(연습)" → 연습용 샘플 3장을 보여주고 **내려받기**를 제공한다(앱 안에서 보는 이미지).
  2. 사용자가 **이미지 파일 올리기**로 그 파일을 올린다(카메라는 열지 않는다).
  3. `js/ocrdemo.js`가 올린 파일의 **이름(keeping-sample-envelope-N)과 PNG 이미지 크기(900×1260)**가 샘플과 같은지 확인한다(파일 내용 해시는 쓰지 않는다: 내려받는 과정에서 파일에 메타데이터가 덧붙어 내용이 달라질 수 있다). 같으면 **인식 연출**(이미지 위에 약 이름 줄을 위에서 아래로 차례로 하이라이트, `manifest.json`의 `box` 사용) 후 "약 N개를 찾았어요".
  4. 봉투에 쓰인 약 이름(`ocrText`)마다 **실제 약 검색**(`dur.search`)을 실행해 후보를 보여주고, 사용자가 **확인·수정**한 뒤 등록한다. 용량·횟수·일수(`dose`)도 함께 불러온다.
  5. 샘플이 아닌 이미지(이름을 바꿨거나 크기를 바꿔 다시 저장한 샘플 포함)는 **인식하지 않는다**: "연습용 샘플 이미지만 인식해요. 실제 사진 인식은 아직 지원하지 않아요." + 샘플 보기 링크.
- **정직함 규칙**: 인식은 시연이고 그 뒤의 약 검색·등록·타임라인 반영·안내는 실제다. 화면에는 항상 "연습용 샘플만 인식해요" 문구를 둔다. 올린 파일은 이 기기 밖으로 나가지 않는다(파일 앞부분 32바이트에서 이미지 크기만 읽는다). 발표에서는 "**글자 인식(OCR)은 시연(미구현), 이후는 실제**"라고 말한다.
- 샘플은 가상이다(환자 "홍길동(예시)", "예시약국"). 실제 처방·환자·약국과 무관하다.
- 샘플 이미지와 목록은 `scripts/make_sample_envelopes.py`가 만든다. 시나리오: ① 평소 먹던 약(씬지로이드) ② **새 처방**(넥시움 + 알마겔에프) ③ 약이 여러 개(시바스·메토폴·무코스타).
- 새 처방 흐름 N2의 "약봉투로 추가(연습)"가 이것이다. 온보딩 O2에도 같은 버튼을 둔다.

### 5-2. 새로 만드는 것: **허가사항 자동 추출 데이터** (성분 단위)

**결정(10/29): 예시·큐레이션 방식은 쓰지 않는다. 누가 어떤 약·영양제를 검색해도 같은 방식으로 안내가 나와야 한다.** 그래서 약 카드를 손으로 만드는 대신, **허가사항(사용상의 주의사항·용법용량)을 자동으로 읽어서 정리하는 파이프라인**을 만든다.

**규모**: 급여목록 제품 21,498개는 **성분 이름 2,105개**(단일 성분 1,622 + 복합제 조합 483)로 묶인다. 같은 성분은 허가사항이 거의 같으므로 **성분당 대표 제품 하나의 문서**만 처리하면 된다. 상위 500개 성분이 제품의 85%, 1,000개가 94%를 덮는다(우선순위: 많이 쓰이는 성분부터).

**파이프라인**
1. **수집** (경로 확인됨, 10/29): 허가정보 API `getDrugPrdtPrmsnDtlInq08`의 응답에 **효능효과(EE_DOC_DATA)·용법용량(UD_DOC_DATA)·사용상의 주의사항(NB_DOC_DATA) 본문**이 XML 문자열로 들어 있다. 같은 응답에 `ITEM_SEQ`, `EDI_CODE`(우리 제품코드와 같다), `MAIN_ITEM_INGR`, `MAIN_INGR_ENG`, **`ATC_CODE`**(약효 분류), `ETC_OTC_CODE`(전문/일반), `CHANGE_DATE`, 원문 PDF 주소(EE/UD/NB_DOC_ID)가 있다. 성분당 대표 제품 하나를 목록 API(`item_name`)로 찾아 `ITEM_SEQ`를 얻고 상세 API를 한 번 부른다(성분당 호출 2회, 총 약 4,200회).
2. **문장 분해**: 문서를 항목·문장 단위로 쪼갠다("6. 상호작용 12)" 같은 위치를 남긴다).
3. **규칙 추출** — 해석을 하지 않고, **원문 문장을 골라낸다**:
   - 복용 시점·식사 관계: "식후 30분", "공복", "식전" 등이 든 용법 문장
   - 간격: "N시간 간격" 표현이 든 문장과 숫자
   - 영양제·음식·일반의약품 키워드(칼슘, 철, 마그네슘, 아연, 비타민K, 오메가-3, 세인트존스워트, 비오틴, 자몽, 알코올, 우유, 카페인·커피, 제산제, PPI …)가 든 **상호작용 문장**
   - 임부·수유부, 고령자 항목
4. **저장**: 성분 단위 JSON(`data/care/by-ingredient/…`). 모든 추출에 **원문 문장, 위치, 출처 URL, 가져온 날짜, 추출 규칙 이름**이 붙는다.
5. **앱**: 등록한 약의 성분 → 추출 데이터 조회 → 등록한 영양제 키·다른 약의 성분과 **키워드 매칭** → 타임라인의 주의로 반영. 앱 실행 중에는 LLM을 호출하지 않는다.

**등급**: 자동 추출은 모두 **②(설명서 근거)**로 표시하고 **원문 문장을 항상 보여준다**. 추출이 틀릴 수 있으므로 "설명서 원문 보기" 링크를 둔다. 해석이 필요한 문장(분류 표현 → 우리 성분 연결)은 `data/care/groups.json`의 구성원과만 연결한다(이름이 비슷하다고 추측하지 않는다). 규칙에 걸리지 않는 약은 "설명서에서 복용 시점·상호작용 안내를 찾지 못했어요"(③)로 표시하고, 병용금기(①)는 그대로 확인한다.

**검증(발표의 "수치로 확인"에 쓴다)**: 사람이 원문을 읽고 정답을 만든 약 20~30개를 **정답지**로 두고, 자동 추출의 정밀도·재현율을 잰다. `data/care/levothyroxine.json`(직접 읽어 만든 6개 규칙)은 **첫 정답지**다. 자동 추출이 이 6개를 다시 찾아내야 한다.

### 5-3. 엔진 출력 형식 (`js/care.js`, Claude 담당)

화면은 이 형식만 읽는다. (화면 작업은 이 형식의 **고정된 샘플**로 먼저 시작할 수 있다.)

## 9. CLAUDE.md 개정안 (Claude Code가 반영)

"서비스 원칙" 1~6을 다음으로 바꾼다.

1. **근거 등급제.** 판단은 근거가 있는 만큼 한다. 등급: ① 공식 지정, ② 허가사항 근거(+참고), ③ 근거 없음(말하지 않는다).
2. **모든 판단에 등급 배지·원문 일부·출처 링크·확인일**을 붙인다. 의학 문구는 요약하지 않고 원문 일부로 보여준다.
3. **없음은 안전이 아니다.** "안전하다/괜찮다/문제없다/먹어도 된다"는 쓰지 않는다.
4. **복용 중단·용량 변경·진단 지시를 하지 않는다.**
5. **근거가 없으면 말하지 않는다.** 등록은 항상 되고 "확인 못 함"으로 표시한다.
6. **확인하지 못한 것은 사실처럼 쓰지 않는다.** 시연(OCR·알림)은 시연이라고 밝힌다.
7. 런타임에 LLM을 호출하지 않는다. 화면의 근거 문장은 **허가사항 원문에서 규칙으로 골라낸 문장**(자동 추출)이고, 규칙은 사람이 만든 정답지로 정확도를 검증한다.

"데이터 팩 규칙"에 추가: 자동 추출 결과(`data/care/`)의 모든 항목에는 **원문 문장·위치·출처 URL·가져온 날짜·추출 규칙 이름**을 붙인다. 사람이 원문과 대조한 정답지(`levothyroxine.json` 같은 것)만 `verified: true`로 표시하고, 약학정보원 등 제3자 편집 화면의 문장을 복제하지 않는다. 분류 표현은 `groups.json`에 적힌 구성원과만 연결한다(이름이 비슷하다고 추측하지 않는다).

## 10. 알려진 이슈 / 미확인

- `dur.js`의 `cleanIngr` 단위 목록에 `㎍` `㎎`(호환용 단위 문자)가 없어 '씬지록신정50마이크로그램'의 성분명 'levothyroxine sodium 50㎍'이 정리되지 않는다 → `care.js`에서 prefix 비교로 우회하고, `dur.js`에 단위 추가(허락 필요).
- 레보티록신 카드의 원문은 약학정보원 화면에서 읽었다. **식약처 원문과의 대조가 아직 안 됐다.**
- 철분제와 레보티록신은 허가사항에 "간격에 주의"라고만 있고 시간이 없다. 칼슘만 "최소 4시간"이다. 철분·마그네슘·종합비타민까지 4시간이라는 말은 약사 복약지도 기사에 나오는 말이라 근거가 아니다.
- 분류 표(`groups.json`)는 아직 `products.json`의 성분명과 대조하지 않았다.
- 상세 API 요청 변수 이름(품목기준코드를 넣는 칸)은 아직 확인하지 못했다. 수집 스크립트가 활용 명세에서 확인한다. 응답 형식은 레보티록신 1건으로만 확인했다(약마다 항목 제목·번호 형식이 다를 수 있다).
- 추출 규칙(`scripts/care_extract.py`)은 레보티록신 1개 약의 정답지로만 시험했다. 정답지를 20~30개로 늘려 정확도를 재야 한다. 첫 시험에서 "비타민K의존성 응고인자"가 비타민 K 영양제로 잡히는 오탐을 발견해 고쳤다(이런 오탐이 더 있을 수 있다).
- ATC 코드로 분류 표(`groups.json`)를 자동으로 만들 수 있다(예: PPI는 A02BC). 아직 하지 않았다.
- 자동 추출은 틀릴 수 있다. 원문 문장을 항상 함께 보여주고 정답지로 정확도를 잰다. 문서 형식이 약마다 다르므로 규칙은 보수적으로(걸리는 문장만 고른다).
- 복합제 성분 조합(483개)은 개별 성분의 문서를 합쳐서 보지 않는다(성분별 매칭은 후순위).
- 의료적 판단을 하는 앱이 규제 대상인지는 확인하지 못했다. 출시를 생각한다면 법적 검토가 필요하다(수업에서는 한계로 밝힌다).
- 임부금기·효능군중복·노인주의 파일의 항목과 이용 조건은 확인하지 못했다.
