# 키핑 (Keeping)

> 내 하루 복약, **근거 있게** 챙겨요.

먹는 약과 영양제를 담으면 하루 복약 타임라인을 만들고, 공식 자료에서 **근거가 확인된 주의만** 알려주는 서비스입니다.
공식 자료(식약처 DUR·의약품 설명서 등)에서 확인한 범위만 보여주고, **판정하지 않습니다.**

## 하는 일 / 하지 않는 일

| 하는 일 | 하지 않는 일 |
|---|---|
| 약·영양제를 검색해서 등록 (모르는 것도 이름으로 등록) | "같이 먹어도 된다/안 된다" 판정 |
| 등록한 것끼리 **겹치는 근거**만 찾아서 보여주기 (출처·확인일 포함) | 설명서를 요약해서 대신 말하기 |
| 복용 시간을 넣으면 하루 시간표 + 설명서에 적힌 복용 간격 표시 | 처방 정보 자동 연동, 푸시 알림 (준비 중) |
| 약사에게 물어볼 질문 만들기 | 음식↔약 상호작용 확인 (근거 데이터 미확인. 음식은 기록만) |

## 실행해 보기 (README만 보고 따라 하기)

필요한 것: Python 3 (또는 아무 정적 서버). 설치할 것은 없습니다.

```bash
cd keeping
python3 -m http.server 8080
# 브라우저에서 http://localhost:8080 열기
```

**시작하기** → 약 검색(예: `시바스`, `이텍스`, `알마겔`)에서 약을 고르고 "담기 확인" 화면에서 먹는 시간을 정해 담기 → 영양제(성분 검색·해외·직접 입력) 순서로 진행합니다. 영양제 검색은 서버 없이도 성분 목록에서 바로 찾아집니다.

`index.html`을 더블클릭해서 여는 방식(`file://`)은 데이터 팩이 JS 파일이라 로드되도록 만들었지만, 실제 브라우저에서는 확인하지 못했습니다. 위의 서버 실행 방법을 권장합니다.

## 허가사항 수집 (scripts/fetch_labels.py)

식약처 의약품 허가정보 API(공공데이터포털)에서 성분 단위로 허가사항 본문을 받아 근거 문장을 추출합니다. 인증키는 환경변수 `DATA_GO_KR_KEY`(`.env`)에서만 읽고, 출력·파일에 쓰지 않습니다.

- **성분 묶기**: `data/dur/products.json`의 급여목록 제품(구분 0·1)을 `js/dur.js`의 `cleanIngr`와 같은 규칙으로 정리한 성분 이름으로 묶고, 제품 수가 많은 성분부터 처리합니다. `--limit N`으로 상위 N개만 돌립니다.
- **대표 제품 기준**: 성분마다 하나만 고릅니다. ① 전문의약품 우선 → ② 내복 우선 → ③ 제품코드 오름차순. (제품 파일에 허가일이 없어서 "최근 허가일" 기준은 쓰지 않습니다.) 그래서 **대표 제품의 설명서가 그 성분의 모든 제품을 대표하지는 않습니다.** 제품마다 문구가 다를 수 있고, 화면은 항상 어느 제품의 설명서인지(`itemName`, `changeDate`)와 원문 링크를 함께 보여야 합니다.
- **품목기준코드 확인**: 목록 API(`item_name`)로 찾은 항목의 `EDI_CODE`가 제품코드와 같을 때만 씁니다. 다르거나 목록에 없으면 "미해결"로 기록하고 다른 제품으로 바꿔 시도하지 않습니다.
- **저장**: 원본 응답 `data/care/raw/`(git 제외, 이어받기용), 성분별 결과 `data/care/by-ingredient/`, 진행 상태 `data/care/progress.json`, 요약 `data/care/summary.json`. 규칙이 0개인 성분도 저장합니다.
- 호출은 순차이고 하루 9,800건에서 멈춥니다. `--reextract`는 호출 없이 받아 둔 원본으로 규칙만 다시 뽑습니다.

## 겹침을 찾는 규칙

| 근거 | 신뢰 | 내용 |
|---|---|---|
| `pair` | 높음 | DUR 병용금기 쌍으로 등록된 경우 (성분 코드 기준) |
| `name` | 높음 | 한쪽 설명서에 상대 약의 **성분 이름**이 직접 적힌 경우 |
| `class` | 낮음 · 약사 확인 권장 | 설명서가 약의 **종류**로 적은 표현(예: "궤양 치료제")에 상대 약이 해당할 수 있는 경우 |
| `supp` | 낮음 · 약사 확인 권장 | 설명서가 적은 표현(예: "철(Fe)염 제제")이 등록한 영양제 성분과 겹칠 수 있는 경우 |

상태: **확인 필요**(근거를 찾음) · **겹침 없음**(확인한 자료 안에서 못 찾음, 안전하다는 뜻 아님) ·
**공식 정보 있음**(식약처 병용섭취정보 33종 원료) · **확인 못 함**(키핑이 확인하는 범위 밖).

## 데이터 팩 (data/datapack.js)

모두 2026-10-28에 공식 화면·API 응답에서 직접 확인한 값입니다.

- 약 7개: 허가정보(제품명 → 구분·성분), DUR 병용금기·효능군중복·품목정보
- DUR 병용금기 쌍 1개(이트라코나졸 × 심바스타틴)
- 설명서에서 읽은 문구 2건(이텍스시메티딘정, 알마겔에프현탁액)
- 영양제 2건(메가도스C 비타민C 3000mg, 서로 다른 신고번호 2건)
- 식약처 의약품 병용섭취정보 원료 33종 목록, 성분 사전

값을 추가할 때: 공식 화면에서 확인 → 출처·확인일 기재 → `node tests/engine.test.js`. 추측으로 채우지 마세요.

## 배포

**A. GitHub Pages (정적, 데이터 팩 모드)** — 가장 쉬운 방법
저장소에 올리고 Settings → Pages에서 루트(`/`)를 지정합니다. 이 경우 검색은 데이터 팩 안의 약·영양제만 됩니다.
(팩 밖의 이름은 "이름으로 등록"하면 "확인 못 함"으로 저장됩니다.)

**B. Vercel (서버 중계 포함, 더 넓은 검색)** ⚠ 서버 코드는 아직 실제 호출로 검증하지 못했습니다.
1. 저장소를 Vercel에 연결합니다. (`api/` 폴더가 서버 함수가 됩니다)
2. 환경변수를 입력합니다: `FOODSAFETY_KEY`, `DATA_GO_KR_KEY`, `DRUG_LIST_OP`, `DRUG_NAME_PARAM`
   (`DRUG_LIST_OP`, `DRUG_NAME_PARAM`은 공공데이터포털 활용 가이드에서 직접 확인해 넣으세요)
3. 배포 후 `/api/supp?name=메가도스`로 응답을 먼저 확인합니다.
4. 정적 페이지를 다른 곳에 두었다면 `config.js`의 `proxyBase`에 서버 주소를 넣고, 서버에 `ALLOW_ORIGIN`을 설정합니다.

⚠ **인증키는 절대 코드·`config.js`·README에 넣지 마세요.** 환경변수로만 관리합니다.

## 한계 (솔직하게)

- **지원 범위**: 약 검색 범위는 약제급여목록 기준 제품 21,498개(전문 20,174 · 일반 1,324)와 병용금기 파일에만 있는 제품 1,628개, 모두 23,126개이고, 병용금기는 23,619쌍(성분 기준)입니다(`data/dur` 기준). 설명서 상호작용을 확인한 약은 데이터 팩의 2개(이텍스시메티딘정·알마겔에프현탁액)뿐입니다.
- **데이터 팩 모드(전체 약 목록을 불러오지 못했을 때)**: 데이터 팩에는 약이 7개 있고, 그중 완전히 확인한 것은 6개입니다(브로목틸정 40mg은 일부만 확인). 설정 화면의 "근거를 확인하는 약 6개"는 이 수입니다.
- **급여목록에는 일반의약품 대부분이 없습니다.** 일반의약품은 급여 대상 1,324개만 있어서, 약국에서 사는 일반의약품 대부분과 비급여 전문의약품은 검색되지 않습니다. 목록에 없는 약·영양제는 이름으로 등록은 되지만 겹침 확인은 되지 않고 "확인 못 함"으로 표시됩니다.
- **병용금기 목록만 확인합니다.** 연령금기·임부금기·용량주의·효능군중복·설명서의 상호작용 문구는 이 데이터로 확인하지 않습니다. 병용금기에서 "찾지 못했다"는 안전하다는 뜻이 아닙니다.
- **영양제와의 상호작용 근거는 제한적입니다.** 공식 병용섭취정보는 33종 원료만 다루고, 비타민 C·이노시톨 등은 범위 밖입니다. 설명서의 분류 표현은 낮은 신뢰로만 연결합니다.
- **등록하지 않은 약은 찾을 수 없습니다.** 결과는 "등록한 N개 기준"입니다.
- **처방 정보 자동 불러오기는 구현하지 않았습니다.** 공식 개인용 조회 경로는 있으나 민간 서비스가 연동하는 정식 경로의 현재 상태는 확인하지 못했습니다.
- **해외 영양제**: 미국 NIH DSLD 중계는 아직 없습니다. 현재는 "직접 입력"(이름 + 성분 선택)으로 등록합니다.
- 후로스판정·브로목틸정의 설명서는 읽어 두지 않았습니다(화면에 "확인하지 못했어요" 표시).
- 후로스판정·브로목틸정·알마겔의 효능군중복 조회 결과는 캡처 순서대로 해당 약의 값이라고 가정했습니다.
- 예시 사용자의 복용 이력(이트코나졸캡슐 등)은 **가정**입니다. 전체 약 목록을 불러오지 못한 데이터 팩 모드에서는 이전처럼 코니트라캡슐(허가정보에 수출용으로 표기된 제품, 데이터 확인용)을 씁니다.
- **같은 쌍이라도 자료에 따라 사유·고시일이 다를 수 있습니다(원인 미확인).** 예: 시바스정 × 이트라코나졸은 병용금기 원본 파일에는 한 버전(2004-01-16)만 있고, 데이터 팩의 조회값(2009-03-03, "횡문근융해증")과 다릅니다. 화면에는 각 출처의 값을 섞지 않고 그대로 보여줍니다.
- 실제 푸시·처방 연동은 없습니다.
- 의료 조언이 아닙니다. 약과 영양제를 같이 먹어도 되는지는 약사나 의사에게 확인하세요.

## 개인정보

건강정보(등록한 약·영양제·복용 시간)는 **사용자 기기의 localStorage에만** 저장되며 서버로 보내지 않습니다.
서버 중계로 나가는 요청에는 제품 이름만 담깁니다. 설정에서 내보내기/가져오기/전체 삭제를 할 수 있습니다.

## 2차 프로젝트: 계정 + 서버 저장으로 전환

- `js/storage.js`의 내부만 서버 호출로 교체합니다. (화면 코드는 이 모듈만 사용)
- 항목에는 처음부터 `id`, `updatedAt`, 스키마 `v`가 있어 병합·마이그레이션이 가능합니다.
- 첫 로그인 시 "이 기기의 데이터를 계정에 올릴까요?" 화면, 서버 저장 동의, 보관·삭제 정책이 필요합니다.
  건강정보 처리의 법적 요건은 별도로 확인해야 합니다.

## AI 활용 과정 (발표 5번 재료)

- 규칙 파일: `CLAUDE.md` (판정 금지, 출처 필수, 없음 ≠ 안전, 키 보안)
- 프롬프트가 바뀐 지점: "주의사항을 다 보여준다" → "내가 등록한 것과 겹칠 때만"
- AI 실수를 잡아 고친 사례
  1. "DUR 품목정보 API가 성분 코드를 준다"는 안내가 틀림 → 실제 응답으로 확인해 정정, 성분 코드는 효능군중복 API에서 얻음
  2. 병용금기 0건을 "기능 문제"로 추측 → 인증키 누락·예시 값 잔존이 원인이었음을 대조 실험으로 확인
  3. "알마겔 설명서에 영양제 언급이 없다"는 말을 비타민 C·이노시톨에 한정해 정정 → "철(Fe)염 제제" 표현 발견
  4. "낮 시간에는 호출 한도 때문에 저녁에 테스트"라는 안내를 정정 → 공용 샘플 주소의 한도였고 개인 키는 호출됨
